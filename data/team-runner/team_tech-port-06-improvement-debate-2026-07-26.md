## 3. 6단계 개선 방향 토론 — claude-code 저성공률 대응 옵션 비교

### ① 직접 이식 (claude-code 실행 경로를 codex의 OrchestratedLoop/실행 방식으로 그대로 대체)
- **유지보수 비용**: 낮음 — 이미 검증된 codex 경로(93% 성공)를 재사용, 별도 유지보수 표면 최소화
- **종속성**: claude-code Type A(Native) 고유 실행 루프를 폐기하고 Type B 패턴에 종속 — NCO의 "3-타입 에이전트" 설계 전제 자체가 흔들림
- **복잡도**: 중간 — 인터페이스 변환은 필요하나 신규 로직 작성은 최소
- **운영 위험**: 높음 — claude-code가 Type A인 이유(자체 실행 루프, 도구 네이티브 지원)가 있다면 이를 무시한 직접 이식은 기능 손실을 유발할 수 있음
- **장기 로드맵**: claude-code의 우위(자체 도구 생태계)를 스스로 포기하는 방향이라 로드맵과 충돌 소지
- **반대 의견/반례**: claude-code의 낮은 성공률이 실행 루프 결함이 아니라 프롬프트/컨텍스트 문제라면(미확인), 직접 이식은 원인을 잘못 짚은 대증요법이 됨

### ② 래퍼·어댑터 (claude-code 앞단에 codex식 재시도·검증 레이어만 추가)
- **유지보수 비용**: 중간 — 원본 로직은 유지, 래퍼만 추가 관리
- **종속성**: 낮음 — 기존 Type A 경계를 보존하면서 실패 처리만 표준화
- **복잡도**: 낮음~중간 — 기존 아키텍처(src/agent/) 변경 최소
- **운영 위험**: 낮음 — 실패 시 fallback만 추가되므로 회귀 위험 작음
- **장기 로드맵**: 3-타입 분류 유지와 정합적, 점진적 개선에 적합
- **반대 의견/반례**: 24h 실패 84건이 재시도로 해결 가능한 일시적 오류가 아니라 구조적 실패(예: 권한/도구 미지원)라면 래퍼는 증상만 가릴 뿐 근본 해결이 안 됨 — 이 가능성은 이번 데이터로 배제 불가(미확인)

### ③ 부분 포팅 (codex의 실패 분류·재시도 로직만 claude-code 실행 경로에 이식, 전체 루프는 유지)
- **유지보수 비용**: 중간 — 두 실행 경로 간 로직 일부가 중복/분기되어 관리 포인트 증가
- **종속성**: 중간 — codex 내부 모듈과 부분적으로 결합
- **복잡도**: 높음 — 어느 부분을 분리 이식할지 경계 설정이 까다로움, 두 시스템 동기화 필요
- **운영 위험**: 중간 — 부분 이식 후 남은 로직과의 정합성 검증 부담
- **장기 로드맵**: 유연하나 "부분"의 범위가 계속 넓어질 위험(스코프 크립)

### ④ 자체 재구현 (claude-code 전용 실패 처리·라우팅 로직을 처음부터 설계)

- **반대 의견/반례**: 원인 진단(왜 18%인지) 없이 재구현부터 시작하면 동일한 문제를 재현할 위험. 최소한 원인 분류 데이터(에러 타입별 breakdown)가 선행되어야 함 — 이번 주입 데이터에는 없음(미확인)
