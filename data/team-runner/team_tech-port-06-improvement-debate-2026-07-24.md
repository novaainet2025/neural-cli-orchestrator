### 전략 1: 직접 이식 (Direct Porting)

| 차원 | 평가 | 반론/반례 |
|------|------|-----------|
| **유지보수 비용** | 초기 중간·장기 낮음. 원본 동기화 부담 없음 | 대상 코드가 활발히 발전 중이면 fork 비용 큼 |
| **종속성** | 원본 런타임 종속성 전체 승계. 충돌 위험 있음 | platform-dependent 코드(Node→Python 등)는 직접 불가 |
| **복잡도** | 단순 copy+adapt, 최소 재설계 | 타입 시스템 불일치 시 adapter 계층이 오히려 늘어남 |
| **운영 위험** | 원본 검증된 동작 그대로. 회귀 적음 | native 기능(TypedArray, Worker)과 충돌 시 추적 어려움 |
| **로드맵 적합** | 일회성 migration 후 독립 진화 가능 | **반례:** codex 성공률 94%여도 6% 실패(2333×0.06≈140건)가 존재 — 직접 이식한 모듈이 140건 패턴에 걸리면 발견 어려움 |

**codex 판단**: codex(94%)에 위임 시 직접 이식의 실행 리스크는 낮은 편. 단, claude-code(35%)가 직접 이식하면 실패 확률 65% — 절대 금지.

### 전략 2: 래퍼·어댑터 (Wrapper/Adapter)

| 차원 | 평가 | 반론/반례 |
|------|------|-----------|
| **유지보수 비용** | 장기 중간~높음. 원본 API 변경 시 adapter 재작업 | 2개 코드베이스 동기화 부담 지속 |
| **종속성** | 원본에 commit-to-commit 결합. 업스트림 중단 = 블로킹 | adapter 계층 테스트 추가 필요 (현재 커버리지 미확인) |
| **복잡도** | 낮음. 기존 코드 무변경 | error propagation 계층 누적 → 디버깅 어려움 증가 |
| **운영 위험** | 전환기 안전. rollback 용이 | **반례:** adapter 내부 상태 관리 누락 시 silent data corruption — 3/9=33% 실패율 팀에서 발견 어려움 |
| **로드맵 적합** | 단기 MVP·점진 교체 전환기 최적 | adapter 영구화(technical debt) 위험 높음 |

**핵심 트레이드오프**: 팀 완료율 66.7%(6/9)는 adapter 유지보수 부담을 감당할 여유가 충분하지 않음을 시사. 3건의 실패 중 adapter 관련 실패인지는 **미확인** — `/api/teams` 상세 에러 코드 조회 필요.

### 전략 3: 부분 포팅 (Partial Porting)

| 차원 | 평가 | 반론/반례 |
|------|------|-----------|
| **유지보수 비용** | 중간. 경계 인터페이스 관리 필요 | hot-path만 포팅 시 cold-path 원본 유지 → 2개 유지보수 |
| **종속성** | 부분적. 핵심만 분리 | 경계에서의 타입 변환·에러 매핑 누락 위험 |
| **복잡도** | 중간~높음. "무엇을 포팅할지" 결정이 설계 복잡 | **반례:** 80/20 법칙 — 20% 코드로 80% 기능. 나머지 20% 기능이 edge case에서 critical failure — 6/9 완료 팀은 이 패턴 탐지 능력 **미확인** |
| **운영 위험** | 점진적 전환. 위험 분산 | 포팅된 부분과 원본 간 latency asymmetry |
| **로드맵 적합** | 장기 migration 전략에 적합 | 결정 비용(분석 시간)이 실행 비용보다 클 수 있음 |

**실데이터**: opencode(73%) 설계 + codex(94%) 구현 조합에 가장 적합한 전략. opencode가 포팅 범위 분석, codex가 실제 포팅 실행.

### 전략 4: 자체 재구현 (Self-Reimplementation)

| 차원 | 평가 | 반론/반례 |
|------|------|-----------|
| **유지보수 비용** | 초기 높음·장기 낮음. 완전한 소유권 | **반례:** "not invented here" syndrom — codex 94%라도 재구현 품질이 원본보다 나을 보장 없음 |
| **종속성** | 최소. 제로 외부 종속성 | 핵심 알고리즘 재구현 시 검증 시간↑ |
| **복잡도** | 높음. 전체 재설계 + 재검증 | 요구사항 역공학(reverse engineering) 누락 위험 |
| **운영 위험** | migration 기간 중 위험 최대 | **반례:** behavioral regression 발견 어려움 — 3/9 실패 중 1건이 재구현 관련이면, 66.7% 팀이 gap 발견 전까지 진행 |
| **로드맵 적합** | 장기적 최적. 완전한 통제 | 팀 capacity(9건/7일)로 감당 가능한가? 약 1.3 tasks/day — 재구현 단독으로 2~4주 점유 시 일상 업무 마비 |

**핵심 제약**: 현재 throughput 9건/7일. 자체 재구현은 이 용량의 50-100%를 단일 작업이 점유 — 팀 마비 위험. codex 단독 task로 분할 위임 필요.

### 전략 5: 보류·거부 (Defer/Reject)

| 차원 | 평가 | 반론/반례 |
|------|------|-----------|
| **유지보수 비용** | 0 (현행 유지) | 기회비용: 개선 안 하면 경쟁력 손실 |
| **종속성** | 현행 유지 | EOL/EOSL approaching일 경우 미래 위험 |
| **복잡도** | 0 | 해결 지연 → 해야 할 이유 사라질 수 있으나 기술부채 이자 발생 |
| **운영 위험** | 0 (당장) | 장기: domino failure — 한 모듈이 전체 블로킹 |
| **로드맵 적합** | 우선순위 하위일 때 정당화 | **반례:** claude-code 성공률 35%·24h실패 12건 — "이 시스템 자체를 보류"할지 판단해야 하는 지점. 35%는 신뢰 불가 수준 |

**특별 고려**: claude-code 35% 성공률을 개선 없이 방치하는 보류 전략은 운영 위험을 적극적으로 방치하는 결정. 24h실패 12건 = 30분당 1건 — 운영 알림 피로도 심각. 이 부분은 **보류 불가**, 개선 강제 영역.
